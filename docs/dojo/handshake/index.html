01 The Two Streams

A TCP connection is not one channel. It is two.

When two endpoints open a TCP connection, they negotiate two independent sequence-number spaces — one for bytes traveling client→server, one for bytes traveling server→client. The two streams are glued at the endpoints, but their state machines run in parallel. Each side writes into its own outbound stream and reads from the other’s outbound stream. The flows do not cross.

The relay between this Mac and the servers obeys the same shape. L’s outbound stream is ~/Public/claude/<sender>/. The remote agent’s outbound stream is ~/Documents/ — the palace. Two writers, two channels, one endpoint per side. Conflate them and the connection is malformed.

kata
On this Mac: sudo tcpdump -i lo0 -nn -S 'tcp port 80' and curl http://havoc/ in another shell. Watch each direction’s sequence number advance independently. That ladder you see is two streams, not one.
02 The Three-Way Handshake

The handshake is the moment both streams are born.

Before any data flows, each side declares its starting sequence number — its ISN, the offset from which it will begin counting bytes outbound. The dance: 

  CLIENT                                  SERVER
    │                                       │
    │  ──── SYN  seq=X         ────>        │   // I'll count from X
    │                                       │
    │  <──── SYN+ACK seq=Y ack=X+1 ────     │   // and I'll count from Y. I heard X.
    │                                       │
    │  ──── ACK  ack=Y+1       ────>        │   // heard Y. ready.
    │                                       │
    │           ESTABLISHED                 │

Three packets. Two sequence numbers negotiated. After this moment, the client is free to write into its outbound stream and the server is free to write into its own — no further coordination required to begin sending. The acknowledgements that follow are about the other side’s bytes, on the other side’s counter.

L’s prior handshake had thamon replying into the client’s outbound space — the equivalent of the server trying to ACK with its own sequence number rather than the client’s. The receiver has no way to interpret that. The fix is to acknowledge in the right space: thamon writes the artifact into the palace; the client (L, or hλvoc) reads it. No reply file. Structural acknowledgement.

kata
Open nc -l 9999 in one terminal and nc localhost 9999 in another. Type into each. Notice that what you type on side A appears on side B — not on side A. The two halves are real. Now Ctrl-D on side A: side A can still receive. Half-close is real.
03 Half-Close, FIN, and Why It Matters

Either side can close its outbound stream alone.

TCP’s teardown is not symmetric in time. One side sends FIN — I have no more bytes to send — and the other side keeps writing for as long as it wishes. The connection lingers in FIN_WAIT / CLOSE_WAIT until both halves are independently retired. Only when both have FINned is the socket gone. 

  A                                          B
  │  ──── FIN seq=M       ────>             │   // A: done writing.
  │  <──── ACK ack=M+1    ────              │   // B: heard. I'm still writing.
  │                                          │
  │       ( B keeps sending bytes... )       │
  │                                          │
  │  <──── FIN seq=N      ────              │   // B: done too.
  │  ──── ACK ack=N+1     ────>             │   // A: heard. closed.

Translation for the relay: when L pulls thamon’s last artifact from the palace, she is not waiting on a goodbye message. She reads the byte and the read itself is the ACK. The palace channel is live for as long as artifacts are still arriving; the brief channel is live for as long as briefs are still being issued. The two close on their own clocks. This is structural acknowledgement again — the same shape, all the way down.

A connection that conflates the two channels cannot do this cleanly. It will try to close both halves with a single act, and one half will be cut while the other is mid-sentence.

kata
ss -tan state established on Eleven during an active rsync from havoc. You will see the connection in ESTAB. Pause the rsync; look again. The connection is still ESTAB — bytes are not flowing, the channel is not closed. Each direction owns its own keep-alive.
